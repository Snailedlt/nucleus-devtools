# AGENTS.md

Guidance for AI coding agents working on **this repository** (`nucleus-devtools`): the SplitScreen.Me VS Code extension, the `ncdev` CLI (old name `nucleus`; also a standalone .exe), the Notepad++ plugin and the agent skill for Nucleus Co-op handlers, and, in `workbench/`, the browser workbench and site (`workbench/playground/`, on GitHub Pages at https://snailedlt.github.io/nucleus-devtools/) and the Jint testbench (`workbench/src/`, `workbench/probes/`). The workbench imports the core from the repository root (`src/core`), so one commit has both; its own rules are in [The workbench](#the-workbench-workbench) below. (The workbench was the repository `nucleuscoop-handler-testbench` until it moved in here; that one is archived.)

If you are writing or fixing a *game handler* rather than this tooling, use the skill in `plugin/skills/nucleus-handler/` (start with its `SKILL.md`).

## Who it's for: a tool for every level

**Priorities, in order:** 1. a great tool for experienced developers and handler authors (correct checks, speed, keyboard, the core features); 2. easy to understand and use for newcomers, without getting in the way of 1.

The tools serve experienced developers, handler authors, Nucleus Co-op experts and complete newcomers alike. Welcome beginners without making the work slower or more cluttered for anyone else. (The model is Warcraft 3's editor: clickable, choices from lists, one-button testing, and a way into real code.)

- **One code underneath.** Everything that edits a handler (the code editor, Lines, pickers, fixes, any visual editor to come) edits the real handler code, so nobody is locked into a beginner mode and people move up a tier by looking at the code.
- **Code first, a visual editor later.** The workbench edits code today (VS Code users write code too: there it means clear hovers and suggestions). The earlier Form and Blocks views were removed; a different visual representation is planned. When it comes: plain-language names next to (or instead of) the API names, tips and docs right where each option is, values picked from lists, and it can be shown or hidden, since most developers never open a visual editor and most newcomers end up in code.
- **Help on request, not on screen.** Markers, hints, plain-language labels and pickers show on hover, tap or a key (Ctrl+Space, Alt+Enter), never permanently in the code.
- **Keyboard first for experienced users.** Everything is reachable from the keyboard and the command palette; no wizard is ever required.
- **The first-run choice only sets defaults.** "Guide me" turns on tips and guided help; "I write code" starts compact. Every part can be switched in Settings. After it, a short tour of the workbench's GUI (`workbench/playground/src/tour.ts`) runs once (never for an automated browser or a link to something specific); Skip remembers the step and *Take the tour* continues or starts over. There is no welcome page: with nothing open, the workbench opens the template.
- **The tool teaches.** Our community is small and won't write many guides, so the explanations live in the tool: plain-language docs on every option, "why" in every problem, examples from real Hub handlers, help that starts from the symptom ("my game pauses when it loses focus").
- **Desktop first.** Over 90% of people write handlers on a desktop or laptop: design and test for that (mouse, keyboard, a wide screen). Phones are supported but not tailored: nothing broken, cut off or untappable, checked by the smoke test's phone checks. No phone-only features, no phone layouts driving a design, no manual phone testing or phone screenshots for every change.
- **The check for every new feature:** does it add anything on screen for someone who didn't ask for it? If so, put it behind a hover, tap or key, or a setting.

## Name and brand

**These are Nucleus Co-op tools under the SplitScreen.Me umbrella** (the maintainer's decision; don't make them remind you). The extension, the workbench, `ncdev` and the Notepad++ plugin are for Nucleus Co-op handlers, so they say **Nucleus** where people look for them: command categories (*Nucleus: Try It*), messages, the output channel, status items, titles. **SplitScreen.Me** is the organisation they belong to: the publisher, the Discord, "part of SplitScreen.Me" in descriptions, About text and footers; settings keys stay `splitscreenme.*`. Tools for other split-screen projects (PartyDeck, UniversalSplitScreen, Proto Input) would be separate extensions/tools under the same umbrella, not more commands in these. Ids, keys and links that already exist keep working (see "Links live for ever").

## Commands

```bash
npm ci
npm run build       # esbuild: dist/extension.js, dist/cli.js, AND the skill's scripts/nucleus.js + reference/api.md
npm test            # build + node:test (dist-test/*.test.js)
npm run typecheck   # tsc --noEmit
npm run package     # .vsix
npm run standalone  # dist-sea/: NcDev.dll (Notepad++ plugin, needs MinGW) + ncdev.exe / ncdev-linux-x64 (Node SEA); then node scripts/smoke-standalone.mjs
npm run check-links # every AI docs source link works (network; CI and the Sync workflow run it)
node scripts/readme-blocks.mjs   # rewrite README.md's generated blocks (--check: are they current? a test runs it)
npm run generate    # regenerate data/nucleus-api.json + types/nucleus.d.ts (needs ../splitscreenme-nucleus and ../splitscreenme-www clones; the Sync workflow does this daily by PR)
claude plugin validate .   # validate .claude-plugin/marketplace.json and the plugin
```

Run `npm test` and `npm run typecheck` before finishing. Run `npm run build` after changing anything under `src/` and commit the regenerated `plugin/skills/nucleus-handler/reference/api.md` (CI checks it). The skill's bundle, `scripts/nucleus.js` (several MB), is committed **only in the release commit** (run `npm run build` there and commit it; the Release workflow refuses a stale one, and CI fails a pull request that changes it without a version bump: `scripts/check-skill-bundle.sh`). Every other commit leaves it as it is (`git checkout -- plugin/skills/nucleus-handler/scripts/nucleus.js`), so the history doesn't grow by a bundle per change. Plugin users get the released bundle from `main`.

## Layout

- `src/core/`: pure logic, no `vscode` import, shared by the extension, the CLI and the skill.
  - `api.ts`: typed access to the generated API model, member resolution.
  - `lint.ts`: the linter (acorn AST). `RULES` is the rule registry.
  - `jsrules.ts`: general JavaScript mistakes from ESLint's own rules (its `Linter`, in-process, `eslint/universal`), each with a plain title and why, merged into `lint()`'s results. Add one only after running it over every Hub handler (the `data` branch's `hub/`) with no false alarms. The Try it sandbox bundle stubs ESLint out (`eslint-stub.ts`); the workbench's build shims `path` and `process` for it.
  - `jsbuiltins.ts`: JavaScript's ES5 objects and methods (String, Array, Math, JSON, Number, global functions) for completion/hover/signature help, from `data/js-builtins.json` (generated from TypeScript's `lib.es5.d.ts` by `scripts/generate-jsbuiltins.mjs`; a test checks it's current).
  - `format.ts`: Format Document / `ncdev format`: indentation and spacing, plus quotes and semicolons as set (double quotes and a semicolon after each statement by default; "keep" leaves them). Line breaks never move and the result is re-tokenized and compared with the original; any difference and it refuses. Keep that guarantee, and say what it changes wherever it's described (not "spacing only").
  - `complete.ts`: text-based resolution for completion/hover/signature help (works on incomplete code).
  - `scopes.ts`: a small scope model of the handler's own variables (what's assigned to them, per function), for checks that follow a value through the handler's code (`option-compare`). Measured against every Hub handler in `docs/spikes/26-deeper-checks.md`.
  - `features.ts`: the editor features as plain data (hover, completion, signature help, quick fixes, Format Document edits, inlay hints, handler detection). `extension.ts` and `lsp.ts` only convert them.
  - `lookup.ts`: `ncdev api` lookup/search and the Markdown API reference.
  - `sim.ts`: "Try it", runs a handler per player emulating Jint. Shared with the browser workbench (`workbench/playground`); keep it free of Node and DOM APIs.
  - `pkgcheck.ts`: checks on a handler's package files (Windows names, overwrites, INI/JSON, a misspelled `Game.Folder` file). `gamefolder.ts`: checks against the game's install folder (ExecutableName, BinariesFolder, the symlink lists). Both shared with the workbench, which imports them.
  - `notepadpp.ts`: the Notepad++ auto-completion file (API names, `System.IO` members, call tips), merged into Notepad++'s own on the user's PC by `ncdev setup notepad++` (`src/setup-npp.ts`) when there's no plugin. Never ship Notepad++'s own file.
  - `report.ts`: reports from every tool (workbench, Learn, VS Code, ncdev, `ncdev lsp`, Notepad++): which repository and issue form a report belongs to (people never pick one), the fields and a details block with the bot's checksum, the text for "Copy the report" (the testers' Discord thread), possible duplicates (GitHub search, cached, quiet on failure), the Hub/Discord/Reddit route for a problem in one handler. `reporticons.ts`: the shared report icons (report, flag, idea) and `reportButton` (icon + text, or icon with the same words as name and tooltip). `src/reportvscode.ts` is VS Code's flow; `nucleus.report` the LSP's; `ncdev report` the CLI's. A test checks every link against the forms.
  - `templates.ts`, `zip.ts`, `pkg.ts`, `hub.ts`: New Handler templates, .nc packages, agent-kit install, hub.splitscreen.me client.
- `src/extension.ts`, `src/commands.ts`, `src/tryit.ts`: VS Code glue (`tryit.ts` is the Try it panel). `src/handlermode.ts`: handlers open in their own language, `nucleus-handler` (JavaScript's grammar, `syntaxes/`), so VS Code's JavaScript service stays out (`splitscreenme.languageMode`); every provider is registered for both languages, and anything contributed for `javascript` in package.json (snippets, breakpoints, semantic scopes, debugger) is for `nucleus-handler` too (a test checks it).
- `src/sandbox.ts`: runs `core/sim.ts` for Node hosts inside a `vm` context. `scripts/build.mjs` bundles `src/sim-sandbox-entry.ts` into a string (`__SIM_SANDBOX__`) for it. That string's copy of the API model leaves the documentation out (the simulator only needs names, kinds and types; a test runs every probe both ways). Never call `simulate()` directly from Node code: handler code would get full Node access. `src/test/sim.test.ts` tries the known escapes. Editors and servers (Try it, Test all, `nucleus.tryIt`, `nucleus_simulate`, the debugger) go through `src/simworker.ts` instead: one worker thread owns the same vm sandbox (`src/sandbox-vm.ts`, bundled to `__SIM_WORKER__` and started with `eval: true`, so the standalone ncdev works), with a hard time limit, a memory limit and cancellation, so a looping handler never blocks the thread that serves people. The synchronous `simulateIsolated` stays for the CLI's one-shot runs and tests.
- `src/pkgfiles.ts`: the files in `<Name>/` next to `<Name>.js` on disk, for the package checks (extension, CLI, LSP). `src/gamefolder-node.ts`: reads a game's install folder from disk (extension and `ncdev lsp`). `src/gamefolders.ts`: VS Code's *Game Folder: Link…*, its problems, fixes and completion (`splitscreenme.gameFolders`).
- `src/dap.ts`: the Debug Adapter (DAP) over `core/debug.ts` (no `vscode` import; `ncdev dap` serves it on stdio for other editors); `src/debugvscode.ts` registers it inline for VS Code's Run and Debug (`"type": "nucleus"`).
- `src/cli.ts`: the `ncdev` CLI (`nucleus` is its old name, `nucleus-lint` an alias of `ncdev lint`).
- `src/standalone.ts`: the standalone ncdev (Node single executable, built by `scripts/sea.mjs` with the pinned `NODE_VERSION`; the skill and the Notepad++ plugin are built-in assets) and `ncdev update` (newest release, SHA-256 checked, the running exe moved aside). `scripts/smoke-standalone.mjs` tests a build; the Release workflow and CI run it.
- `src/setup-npp.ts`: `ncdev setup notepad++`: installs the plugin (`plugins\NcDev\NcDev.dll`, `NcDev.ini` with ncdev's path) and copies ncdev to `%LOCALAPPDATA%\ncdev`; without a built-in plugin, merges the names into Notepad++'s list (`core/notepadpp.ts`). `src/winhelp.ts`: when Notepad++'s folder isn't writable, setup starts itself again with Windows' permission prompt (`--elevated --result-file`, the copy writes what it did); and the menu a double-clicked ncdev.exe shows (only when Explorer started it: no arguments from a terminal still print the help). The prompt can't be tested off Windows: the beta test plan has `notepadpp-install`.
- `npp-plugin/`: the Notepad++ plugin, a thin client of `ncdev lsp` (C++17, MinGW, `build.sh`; Scintilla headers vendored under their own licence, Notepad++'s plugin API declared in `NcDev.cpp`). Keep logic out of it: features go into `core/features.ts` / `lsp.ts` first. Test it in Notepad++ (Wine works: `wine explorer /desktop=…` so popups paint; `NCDEV_PLUGIN_LOG` logs the LSP traffic).
- `src/nucleusrun.ts`: Test in Nucleus Co-op: install, then start `NucleusCoop.exe <GUID>` from its folder (it selects that game; a second copy won't start, so an open one is closed first, with the user's OK); its debug log switch in `Settings.ini`. VS Code, `ncdev test`, `ncdev lsp`, Notepad++ (through `ncdev test`).
- `src/install.ts`: installs a handler and its `<Name>/` folder into Nucleus' `handlers` folder (VS Code's Install, `ncdev install`, the Notepad++ plugin through it).
- `src/hubcache.ts`: every Hub read goes through it. The list comes from our daily index (this repository's `data` branch, `hub-index.json`, from `hub-sync.yml`), revalidated hourly by ETag; the Hub API only as a fallback; packages once per version, shared requests, at most two downloads at once, capped retries on 429/5xx. Every request carries `core/hub.ts` `hubClientHeaders(tool, feature)` (our devtools, the tool, the feature; nothing personal): pass a `feature` from each call site. Keep it that way: don't add direct Hub API calls.
- `src/lsp.ts`: `ncdev lsp`, a Language Server (stdio, Content-Length framed JSON-RPC, no dependencies) for other editors. [PORTING.md](PORTING.md) explains the split and has the config for each editor.
- `src/mcp.ts`: `ncdev mcp`, the same tools as an MCP server (stdio JSON-RPC); `src/aivote.ts` is the AI docs vote (`nucleus_vote_doc`, `ncdev docs vote`). The extension registers it for VS Code's agents. `src/simformat.ts` is the simulation text shared by both.
- `src/test/`: tests. `vscode-mock.ts` stands in for the `vscode` module, via an esbuild alias in `scripts/build.mjs`.
- `scripts/issue-bots.mjs`: the issue bots (`doc-review.yml`, `report-details.yml` call it; the Release workflow, and `pages.yml` for workbench updates, call `runFixedComments`: "Fixed in vX.Y.Z" or "Added in vX.Y.Z", with the release notes link, on the issues a release delivers (marked "(#12)" on their CHANGELOG line, or "Fixes #12" in a commit), this repository's only, once each, never failing the release). `src/test/bots.test.ts` checks them on real issue bodies and against the forms in `.github/ISSUE_TEMPLATE/`; rename a form field and that test fails. The details checksum must match the workbench's (`workbench/playground/src/checksum.ts`; both test the same block).
- `scripts/generate-api.mjs`: builds the API model from the Nucleus C# sources + splitscreen.me docs, `data/claude-*.json` and `data/hub-examples.json`. A doc belongs to the option it is written next to: a `//` comment only on the same line (or directly above one option, no blank line), a table row's description only for the options the row starts with.
- `scripts/build.mjs`: every bundle. `scripts/eslint-slim.mjs` is its esbuild plugin (the workbench's build uses it too): bundles carry only the ESLint rules in `core/jsrules.ts` (ESLint's own rule map lists all ~290) and one copy of acorn. Add a rule to `JS_RULES` and it is bundled; a test checks the two agree.
- `scripts/release-files.sh`: what a release hands out besides the .vsix (ncdev for each target, tested; the Notepad++ plugin's zips, `scripts/npp-zips.sh`; the checksums), for CI and the Release workflow. `data/release-assets.json` lists a release's files with a line each (the release notes and the tools page read it; a test checks `release.yml` uploads exactly those). `.nvmrc` is the Node.js version for working on the tools (the workflows read it).
- **Docs come from data** (keep it that way: add to the data, not to a page). `scripts/readme-blocks.mjs` writes README.md's `<!-- generated:… -->` blocks and gives the workbench's build the same content: the tools' comparison (`data/tools-compare.json`), the editors that use `ncdev lsp` with their test status, tools-page tile and setup steps (`data/editors.json`; the snippets are PORTING.md's own code blocks), what each tool is and how to set it up (`data/tools.json`: the reference and setup pages of the docs' Tools section, and its two diagrams), the checks, settings, commands and MCP tools (from `RULES`, `package.json`, `TOOLS`). `src/clihelp.ts` is `ncdev --help` and the docs' command page. One address each, as constants: the site (`core/sharelink.ts` `WORKBENCH_URL`), this repository and its raw files (`core/report.ts` `TOOLS_REPO`, `REPO_URL`, `DATA_RAW`, `MAIN_RAW`), Discord and Reddit (`core/report.ts`), the Hub (`core/hub.ts` `HUB`). `src/test/docsync.test.ts` checks what docs still say by hand (names of commands, tools, settings, versions) against the code.
- `plugin/`: the Claude Code plugin (`.claude-plugin/plugin.json`, `skills/nucleus-handler/`). `.claude-plugin/marketplace.json` at the root publishes it.
- `docs/images/gallery/`: the VS Code and Notepad++ screenshots, one set per view (`<tool>-<view>-{light,dark}.webp`), shown by the README and by the workbench's start page gallery (its build copies them from here, like `docs/videos/`, and stops if one is missing; the workbench's own are in `workbench/docs/images/gallery`). Retake a view in place, light (Light Modern) and dark (Dark Modern); don't add separate copies.
- `workbench/`: the browser workbench and site, and the Jint testbench: see [The workbench](#the-workbench-workbench).
- `vercel.json`: the workbench's Vercel previews (every pushed branch; the project's root directory is the repository root).
- `.coderabbit.yaml`: CodeRabbit's pull request reviews. It reads this file and the skill's docs as guidelines; its `path_instructions` repeat the rules above per folder (core, rules, format, sandbox, Hub, adapters), so change them together. The Nucleus source reaches it through the DeepWiki MCP server, connected in CodeRabbit's web app. [CODERABBIT.md](CODERABBIT.md) has the web app's setup.

## Docs written by Claude

`data/claude-docs.json` holds API docs Claude wrote from the Nucleus and Proto Input source, for members the official docs and the source comments leave out. Each entry has `doc` and `basis`. **`basis` is data, not a sentence** (`AiBasis` in `core/api.ts`): `source`, a list of `{ "project": "Nucleus", "file": "GenericGameHandler.cs", "what": "StartGame" }` (one file per item; `project` as the source names it: Nucleus, ProtoInputHooks, Proto Input guide, …), `hub: { "counted": "<date>" }` when claims rest on the verified Hub handlers, `engines` (`true`, or the families named, e.g. `["Source"]`) when they rest on `data/hub-engines.json`, and `note` for anything else. Every `project` is in `data/sources.json` (repository, default branch, folder, local clones; or a fixed docs URL; plus the words and links for the Hub and engine data): `npm run generate` (`scripts/sources.mjs`) finds each `file` in that repository's clone and stores its link as the item's `url` in the model: a GitHub permalink at the last commit that changed that file (`/blob/<sha>/<path>`, a folder `/tree/<sha>/<path>`: the last commit that changed something in it), as of the clone's default branch (this repo, `"ref": "head"`: its newest pushed commit), stored as the item's `commit`. So the link shows the file's latest version as of the last `npm run generate` (not necessarily the one the text was checked against: when the file changes, the link moves on and `source-changes.mjs` lists the text to check again), moves exactly when that file changes and never breaks when it moves; a shallow clone is deepened first (history without contents). The tips are in the model's `sourceCommits`, never in sources.json. When a source file's commit moves, the AI-written parts written from it may be out of date: `scripts/source-changes.mjs` lists each such file with its compare link and the parts to check again, and the Sync workflow puts that in its pull request. This repo's own files (`data/hub-engines.json`) must be committed and pushed before `npm run generate` links them; `npm test` fails while one differs from its linked version; a docs page's file links to the published page (its front matter's `slug` or `id`); a file not found warns and gets no link. `npm run check-links` (`scripts/check-source-links.mjs`, network; CI and the Sync workflow run it) fails on a link that doesn't work; `npm test` checks offline that every source has one and GitHub ones are permalinks at the item's `commit`. Add a project there, never a link in code or per entry. Every place builds its text from these fields (`aiBasisItems`: one item per source, linked where it can be): the sparkle's tooltip (`aiTip`: "✨ AI-written", then "Based on" and the items as links; it stays open on hover and focus so they can be clicked), Markdown (`aiBasisMarkdown`, the items as Markdown links on one line), the words for agents (`aiBasisWords`, no links; `scripts/basis.mjs` for the .d.ts and the doc-review bot, tested to agree). `data/claude-param-docs.json`'s `basis` is the same and reaches the model as `paramsBasis`. `npm run generate` uses one only where no human doc exists (or with `"override": true`, where the official text is wrong), and marks the member `docBy: "claude"`, `docBasis`. Every place docs show marks it, and only AI-written parts (the doc, "In practice", an AI-written example, AI-written parameter docs), the same way everywhere, without words on screen: where HTML shows docs (VS Code's Docs panel, the workbench's Docs, the docs pages) the part sits in a framed box with a light AI-violet tint and the sparkle in its corner (`core/aimark.ts`: `placeAiFrames` on `memberMarkdown(…, slots)`, `aiMeta`, `aiFrameCss`); the sparkle's tooltip (hover and focus, Escape closes it) is a short structured list: "✨ AI-written" (with "Checked by …" / "Verified by people" when they apply), then "Based on" and one linked item per source (`aiTip` in `core/aimark.ts`), and a visually hidden "AI-written" tells screen readers. Markdown (hovers, completion, parameter hints) puts a ✨ (`AI_MARK`) before the AI-written text and the basis on its own small line ("Based on …", the same items as links); the Notepad++ call tip shows it as "[AI]". The CLI, MCP and `api.md`, read by agents, keep the words ("AI-written, based on …", `claudeNote`/`practiceNote`; the tools say "AI-written", not Claude). No glow or animation: that is for AI buttons. Human docs stay plain. A person who checks one against Nucleus is recorded with `"checkedBy": "<name>", "checkedOn": "<yyyy-mm-dd>"`: a maintainer adds the name by hand after the check (a `doc-review` issue); anonymous votes never set it; a small "✓ Checked by …" mark then shows next to the sparkle (`aiChecked`), and the frame stays, as does "Verified by people". When you write one, read the source first and state only what it shows; `src/test/docs.test.ts` checks every entry is a real member and still used. `data/claude-param-docs.json` does the same for parameters (what to pass), for the most used methods: they show in parameter hints (a ✨ before each), the Docs panel (in their own frame) and the `.d.ts` `@param`s.

**"In practice" and examples.** `data/claude-practice.json` holds a second, AI-written part per member, kept apart from its doc (human or AI): what it really does in the Nucleus/Proto Input source and, in 1-3 short plain sentences, how, where, why and for which (kinds of) games Hub handlers use it: the typical value in words ("almost always 100; 500 for games that dislike their windows being touched"), the callback it goes in, why authors set it, the engines it shows up in ("mostly Unity games", from `data/hub-engines.json` and the per-engine `engines` in `data/hub-examples.json`), the mistakes they make. **No counts or percentages** ("841 of 899", "(336)"): they go stale. Each entry has `text` and `basis` (the fields above: `source` files and functions, `hub.counted`, `engines`); optional `example` (ES5, lint-clean, within 60 columns once `prettyCode` lays it out) and `exampleIn` (`top`, `Game.Play`, `Game.ProtoInput.OnInputLocked`, ...). Read the source and check in the Hub handlers (`data/hub-examples.json`, or the data branch's `hub/`) before writing one; claim only what they show. `npm run generate` puts it in the model as `practice`/`practiceBasis`, and every place docs show marks it as AI-written as above (the frame, or "✨ In practice" in Markdown). Examples: the official docs' first; else one from claude-practice.json (`exampleBy: 'claude'`, framed or "✨ Example" like the other AI-written parts); else the most common value or call in the verified Hub handlers when at least 5 and a fifth of their users agree (`exampleBy: 'hub'`, from `data/hub-examples.json`, made by `scripts/hub-examples.mjs` from the data branch's `hub/`; labelled just "From Hub handlers", no counts); else, for switches and values, one from the type (`exampleBy: 'generated'`). Each says where it comes from, in a few words and without numbers. `exampleIn` says where the workbench's "Insert into handler" puts it.

**"By engine".** `scripts/hub-engines.mjs` gives each Hub handler its game's engine family (`data/hub-engines.json`): from Wikidata by the handler's `Game.SteamID` (P1733), else by the Hub page's IGDB game (P5794, the Hub index's `gameUrl`), else from the handler's own code (Unreal's `Binaries\Win64`, Unity's `-screen-width`, Source's `-novid`, ...; a definite file layout also beats Wikidata, which has a few wrong). Versions are grouped (Unreal Engine 1-5 → Unreal); Source stays apart from GoldSrc and the id Tech / Quake family. Wikidata's answers are cached in `data/wikidata-engines.json`; only `--refresh` asks query.wikidata.org again (`--check` lists where the code rules and Wikidata disagree). `scripts/hub-examples.mjs` counts per member how many handlers of each family with at least `ENGINE_MIN_HANDLERS` (30) use it (`engines`), and `npm run generate` puts `engineUse` and, where a family is at least twice (or half) the share of all handlers and 15 points apart, the mechanical `byEngine` line in the model, in words without counts ("By engine: more common in Source games, rarer in Unity games."; the numbers stay in `engineUse`). It shows with "In practice" (or alone under that heading), not AI-written. Write engine habits into "In practice" only from what the handlers or the source show, with `engines` in the basis.

**Votes and "Verified by people".** Both parts of a doc get 👍/👎: `doc/<name>` (the doc, human or AI-written) and `practice/<name>` ("In practice"). People vote with the workbench's and the docs pages' buttons (GoatCounter events `vote/<part>/<name>/<up|down>`; a browser driven by a program, `navigator.webdriver`, never sends). AI agents vote with `ncdev docs vote <name> <doc|practice> <up|down>` or the MCP tool `nucleus_vote_doc` (events `aivote/<part>/<name>/<up|down>`), only after checking the doc against the source. `workbench/tools/votes-report.mjs` (in `hub-sync.yml`) sums them daily into the data branch's `votes.json` (`docs`, `practice` for people; `aiDocs`, `aiPractice` for AIs, never mixed); `scripts/doc-votes.mjs` snapshots that into `data/doc-votes.json` (the Sync workflow, daily), and the workbench's build reads the newest `votes.json` itself. The rule (`core/docvotes.ts`): an AI-written part with **at least 10 votes from people and at least 90% of them 👍** is labelled "Verified by people (N votes)", still marked AI-written; AI votes are shown apart ("AIs: 4 👍 1 👎") and never count towards it. The label changes when the tools are next built (no server). The counts are anonymous on purpose (no accounts), so they can be forged by anyone who sends GoatCounter requests directly: "Verified by people" is a hint, not proof. The maintainer accepted that limit; the label that can't be faked is a person's "Checked by" (`checkedBy`, which a maintainer records by hand after that person checked it in a doc-review issue; anonymous votes never set it; it is as reliable as that check).

## Facts the code relies on (verified, don't "fix" them away)

- Nucleus runs handlers with **Jint 2.11.58** (`Master/NucleusGaming/packages.config` in splitscreenme-nucleus). Its parser is ES5 plus `let`/`const`, which behave like `var` (the interpreter ignores the declaration kind), so redeclaring one with `var` loads fine (probe 112; `core/jsparse.ts`). Arrow functions, template literals, classes, spread and destructuring are rejected.
- Jint resolves .NET members with only the **first character** case-insensitive (`ObjectWrapper.EqualsIgnoreCasing`). Writes to unknown members are silently ignored outside strict mode.
- .NET is reachable from handlers (`new Engine(cfg => cfg.AllowClr(assembly))`, GenericGameInfo.cs), so `System.IO.File.Copy` etc. work. `src/core/dotnet.ts` lists the `System.*` members handlers use, as open objects (unlisted names allowed unless they look like a typo). Calling a member that doesn't exist throws `Object has no method 'X'` (probe 116), reading one gives `undefined` (117), and `params` overloads such as `Path.Combine(params string[])` are expanded (114, 115).
- `Context` fields with the same name and type as `Game` fields are copied from `Game` (`GenericGameInfo.CreateContext`).
- `Game.Play` runs per instance (GenericGameHandler: three call sites). Default: after the instance is set up (Goldberg, XInput, ...) and before launch, and `Context.StartArguments` is read after it. `GamePlayBeforeGameSetup` runs it before the setup, `GamePlayAfterLaunch` after launch; both true means never. An exception in it (or in `OnFinishedSetup`) ends the session. `OnFinishedSetup`, `OnStop`, hotkey and Proto Input lock callbacks see the last player's `Context`. `SetupSse` is never invoked.
- Nucleus reads the handler line by line and executes `"\r\n" + line + "\r\n"` per line (GenericGameInfo's constructor), so a string continued with a backslash fails to parse. The testbench harness (`workbench/src/Harness.cs`) does the same.
- Jint 2.11.58 only matches overloads with exactly as many parameters as arguments: C# default values are ignored, so the generator marks no parameter optional (probe 110).
- The Hub install (DownloadPrompt.ExtractHandler; also HubWebView and drag & drop) scans raw lines, comments included, for `line.ToLower().StartsWith("game.executablename" / "game.gamename")`, takes the text between the first and last `"`, stops after two matches, and throws on a matched line with fewer than two `"`. `GameManager.AnyGame` (Search disks) reads `Game.ExecutableName` without a null check.
- `Hub.*` lines (`Hub.Handler.Id/Version`, `Hub.Maintainer.*`) are written by hub.splitscreen.me on upload. Authors don't add or edit them: the model marks them `internal`/`hidden` (no completion), and the linter must stay quiet on them.
- `.nc` packages: `handler.js` at the root, plus top-level folders that need **explicit directory entries**. `Game.Folder` is `handlers/<js file name without .js>/`. A Hub install (DownloadPrompt.ExtractHandler) names that file after `Game.GameName` (raw line value, minus `/ : * ? " < > |`; a backslash stays and breaks the install) and merges the contents of every top-level folder of the package into `handlers/<GameName>/`; other files at the zip root are dropped. A saved profile gives every `Game.AddOption` value back as text (`GameProfile.LoadGameProfile`: `JToken.ToString()`), and Nucleus reads handlers as UTF-8. The simulator uses the Hub install's folder name.

- Proto Input only starts with `Game.ProtoInput.InjectStartup` or an `InjectRuntime_…` option (GenericGameHandler); otherwise every `Game.ProtoInput.*` option is ignored. `BlockedMessages` and the `…Filter` options only act inside its message filter hook (`MessageFilterHook`; ProtoInputHooks `MessageFilterHook.cpp`). A blocked number goes through Proto Input's own message table (`MessageList.cpp`, `GenerateIndexTable`, reproduced in `core/wm.ts`): unlisted numbers land on another entry's switch, numbers past the end do nothing. `data/window-messages.json` comes from that file (`scripts/generate-wm.mjs`, part of `npm run generate`; needs a `../splitscreenme-protoInput` clone). Nucleus spells one option `WindowActvateAppFilter`.
- Options Nucleus only reads inside another's `if` (`needs-option` in `core/lint.ts`): `FakeFocusInterval` and `FakeFocusSendActivateIgnoreKB` need `FakeFocus`; `FakeFocusSendActivate` needs `FakeFocus` or `SendFakeFocusMsg` (WindowFakeFocus); the fake-cursor options need `DrawFakeMouseCursor`; `SteamlessArgs`/`SteamlessTiming` need `UseSteamless`; `Game.ProtoInput.FocusLoop_*` and `FocusLoopIntervalMilliseconds` need `Game.ProtoInput.EnableFocusMessageLoop` (ProtoInputLauncher; skipped when the handler calls `ProtoInput.StartFocusMessageLoop` itself).
- `ProtoInput.Values.GetCursorInfoID` is a Nucleus bug: it holds `RemoveBorderHookID` (ProtoInput.cs ExposedValues), so installing it installs the remove-border hook.

### How the Tools docs are organised

The maintainer asked for docs that are organised and atomic and read like a spec, with getting-started guides only where something has to be installed (2026-11-21). The layout follows what other tools' docs do (Ruff's Editors section, rust-analyzer's book, Vite's CLI and config pages, ESLint's CLI reference, Helix's keymap, and Diátaxis' split between reference and how-to).

- **Two kinds of page, never mixed.** A *reference* page says what a thing is and does: one per tool (`docs/tools/vscode/`, `notepadpp/`, `lsp/`, `ncdev/`, `mcp/`), one per part of the workbench, and the feature comparison. A *setup* page is the getting-started guide of a tool that is installed (`docs/tools/<tool>/setup/`): what you need, the steps, how to see that it worked, then updating. The workbench has none, since there's nothing to install. The docs list groups them as Get started, Workbench, Reference.
- **Every page has the same shape.** Reference: one or two sentences on what it is, a short list of facts (what it runs on, what it needs, where its setup is), pictures, sections named after the thing's own parts, the reference generated from the tool, then Related. Setup: Before you start, Steps, Check that it works, what comes after, Related.
- **A fact has one home.** Write it on the page of the thing it's about, and link there. Shortcuts are written where their feature is described (`{key:<id>}`) and tabulated only on the shortcuts page. What a tool can do compared with the others is on the comparison page only. How the tools fit together is on the Tools page only. Tips aren't repeated on the pages: a page describes the feature and lists the tip under `covers`.
- **Reference describes, setup instructs.** Reference text states facts in plain sentences ("Check runs while you type", "Format never moves anything to another line"), limits included, and gives no advice on when to use the tool. Steps and "you" belong on the setup pages. Both still read as if a person wrote them (Conventions).
- **Few links.** A page ends with one Related list of at most three links, and the text links to another Tools page only where it names that page's subject. No "Next:" lines, no previous/next, no list of the section's pages (the docs list does that). The Tools page and the workbench's overview are the two pages that list others. A test counts.
- **No Hub upload steps yet.** The docs say a `.nc` is the Hub's package format and stop there: they don't tell people to upload to hub.splitscreen.me (the maintainer, 2026-11-21: not before the full release). A test checks the Tools docs' text. Bring the step back with the full release.
- **Adding something.** A new tool gets an entry in `data/tools.json` with `summary`, `facts`, `sections` and `setup`. A new part of the workbench gets a page in `src/guide.json`. A new fact goes on the one page it belongs to.

### Workbench conventions

- Show changes in the preview artifact or the test address first; go live only when the maintainer says so.
- **Links live for ever** (above), in the workbench: addresses end up in Discord posts, READMEs, bookmarks and old releases, so keep them readable and generic (`#docs-Context.ModifySaveFile`, `#hub-<id>`, `#what-it-catches`, not internal ids or tab indexes). When one changes, add it to `MOVED_LINKS` in `workbench/playground/src/links.ts` (workbench `#…` links; `workbench/tools/links.test.mjs` checks every one), keep the old `id` as an alias (start page anchors: `<span id="install" class="anchor-alias">`), or leave a small page at the old path that says what moved and links on (site pages). For something removed, link to a note saying it's gone and what replaced it. An unknown link never dead-ends: it says what it was and offers the way on.
- **Shortcuts are always keys** (keycaps), never plain text or inline code: `kbd.ts` draws them (`kbdify` on rendered HTML, `keysText` for a plain sentence, `keysHtml` for one combination). In UI text and lessons write a combination with a modifier as is ("Ctrl+Z"), a lone key in backticks ("`F8`", "`Esc`"); hand-written HTML uses `<kbd>` per key.
- **Icons come from one set**: `workbench/playground/src/icons.ts` (Lucide, ISC, only the icons used, inline SVG in the text colour; `icon(name)`, `<span data-icon="name">` in page.html), and the core's `reporticons.ts` for reports. No emoji as icons in menus and toolbars.
- **Every code block is syntax highlighted** (above): in the workbench that's docs, hovers, hints, suggestion docs, Check, Try it, the debugger, What's new, the Files panel and the start page, through `codehl.ts` (`hlHtml` for rendered docs, `hlCode(src, mode)` for raw code, `modeFor(name)` for a file by type); plain text (a .txt) stays plain.
- Screenshots come in light and dark (`<name>-light.…`, `<name>-dark.…`); pages show the viewer's theme. One set per view, used everywhere: the start page's gallery and the READMEs show `docs/images/gallery/<tool>-<view>-{light,dark}.webp`: the workbench's in `workbench/docs/images/gallery` (`workbench/tools/screenshots.cjs`), VS Code's and Notepad++'s in the root's `docs/images/gallery` (`build.mjs` copies them, like the videos). Don't add separate copies.

## Conventions

- **Docs and UI text read as if a person wrote them** (the maintainer's request, 2026-11-21). Write the way you'd explain it to someone on Discord: plain sentences, "you", contractions, and the reason behind a thing when it helps. Leave out the habits that give AI writing away: opening with a question ("Not sure what a line does?"), lists of exactly three, a slogan as the last line of a paragraph, one "X: Y" colon sentence after another, two mirrored halves joined by a semicolon, and filler such as *simply*, *seamlessly*, *powerful*, *ensure*. Vary the sentence length, and say a thing once. It applies to the docs' Tools pages (`data/tools.json`, `workbench/playground/src/guide.json`), the tips and the tour, and to anything new. Reference pages state facts instead of addressing the reader, and still follow it ([How the Tools docs are organised](#how-the-tools-docs-are-organised)).
- **Structured and data-driven.** Put content in data (JSON, typed fields) and render it, rather than writing it into strings or code, so it's easy to maintain and reads consistently for people (the AI docs' `basis` is an example: fields, rendered as a list, a line or words wherever it shows).
- **One push per review round.** On a pull request under review, wait until the reviewer (CodeRabbit) has finished, fix every valid comment together, run the checks once and push once; a late or minor comment gets a reply and its fix goes with the next batch, and a wrong one gets a reply and no push. Each push reruns CI and the review, and many small ones make CodeRabbit pause. Verify a comment before acting on it: they are suggestions, and some are wrong.
- When the maintainer has to run a workflow or change a setting, give the direct link (e.g. https://github.com/Snailedlt/nucleus-devtools/actions/workflows/release.yml) and the inputs to enter.
- When you need network allowlist entries (hosts) or environment variables from the maintainer, always list them in a code block, one per line, ready to copy.

- TypeScript strict; keep `src/core` free of `vscode` imports.
- New editor features go in `src/core/features.ts` first (plain data, offsets), then into every adapter: `src/extension.ts` and `src/lsp.ts` (PORTING.md), and the Notepad++ plugin if it needs to show something new.
- **Links live for ever.** Links the tools print or put in docs (the workbench's `#docs-<name>`, `?ref=`, release and Hub links, README anchors, command and setting ids people bind keys to) keep working after any redesign: readable and generic, never internal ids. When one changes, the old one leads to the new place (the workbench's `MOVED_LINKS`; an alias for a command or setting, marked deprecated, pointing at the new one) and says so once. A removed thing gets a note saying what replaced it, not a dead end.
- **Code in docs is laid out neatly**, as prettier would (`core/pretty.ts`: `prettyCode` for examples, `prettySignature` for overloads), at 60 columns, so it reads well in a hover.
- **Every code block is syntax highlighted**, wherever it shows: hovers, hints, suggestion docs, the Docs/Try it panels, the workbench (`codehl.ts`: `hlCode`/`hlHtml`, `modeFor` by file type), the start page. Fenced Markdown gets a language (```` ```js ````/```` ```ts ````) so editors colour it; HTML we render ourselves colours it (`docspanel.ts` `highlightCode`). Inline code that is clearly code is coloured too.
- Handler code you generate (templates, snippets, skill docs) must be ES5 and lint-clean. Tests lint the templates and every `js` block in the skill docs.
- The skill docs must only name real API members. A test resolves every `Game.*`/`Context.*` path mentioned in them.
